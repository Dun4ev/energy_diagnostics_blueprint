# RFC stage03: история оценки и пороги проверки каналов

Адресат: интегратор контрактов и runtime. Код stage03 не меняет общий DTO и policy.

## Контекст

`NumericalAnalyzer.analyze` получает только текущий набор наблюдений и не имеет доступа к хранилищу. При потере свежей температуры он возвращает текущие `score=null`, `priority=unknown`, `status=insufficient_data`. Требование показывать последнюю валидную оценку отдельно от текущей не может быть выполнено одним текущим `AnalysisBundle` без состояния сервиса. Утеря наблюдаемости не должна закрывать ранее открытый case.

В ядре для учебного набора зафиксированы пороги сопоставления каналов: разность основного и независимого датчика >8 °C, допустимое временное расхождение 600 с, stuck при диапазоне основного <=0.05 °C и изменении независимого >=2 °C за 3 ч. Они входят в `modelVersion=deterministic-thermal-0.1.0`, но не представлены в `DiagnosticPolicy`.

## Предложение

1. Runtime хранит последнюю валидную оценку как отдельный read-only snapshot с `analysisRunId`, временем, `modelVersion`, `policyVersion`, входным hash и качеством. Ответ UI явно показывает, что это историческая оценка, когда текущая неизвестна. Не копировать прежний score в текущий AnalysisResult.
2. При следующем пересмотре версии policy обсудить версионируемые пороги `channelSyncSeconds`, `sensorDisagreementC`, `stuckWindowHours`, `stuckPrimaryRangeC`, `stuckIndependentRangeC`; текущие значения не считать эксплуатационными пределами.
3. Для `SeriesPoint` при необходимости добавить структурированные причины исключения точек, сохранив raw observedC. Сейчас `quality=suspect` указывает на спорную точку, но не ее конкретную причину.

До решения интегратора stage03 остается совместимым с замороженным контрактом 0.1.0.
